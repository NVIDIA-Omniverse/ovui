Section 3

Code Organization

ovui provides Python UI building blocks and scene drawing helpers. ovwidgets combines them into an application, common Python classes, and app widgets. Data adapters feed those widgets from real or mock data, with OpenUSD adapters as one concrete backend.

The flow starts with ovui widgets and scene parts, grows into app widgets in ovwidgets, then reaches data through common adapters and OpenUSD adapters.

UI framework

The lowest starting point is ovui. Its package name is ovui, and Python code imports the widget API as omni.ui. A small app opens a Window, builds inside window.frame, and uses stacks, fields, sliders, menus, and value models to hold state and react to input.

  • Window, Frame, Workspace, and DockSpace give apps visible places to put UI.
  • Button, Label, TreeView, StringField, FloatSlider, ProgressBar, Menu, and MenuItem are common widget classes.
  • ui.run() and ui.next_frame() keep input, drawing, and async Python work moving with each frame.

Read this part when the change is about base widget behavior, style helpers, value models, frame timing, or standalone window startup.

Scene tools

The scene helpers live in omni.ui.scene. They add 3D drawing and input helpers that can sit inside a normal UI window, so a viewport can combine regular widgets with camera motion, picking, and transform handles.

  • Main names include SceneView, Scene, Manipulator, CameraModel, and GestureBinding.
  • The package covers geometry, labels, images, camera interaction, picking, and manipulator behavior.
  • The viewport uses these pieces for camera movement, selection outlines, transform handles, and HUD content.

Read this area when a feature needs scene drawing, gesture handling, or a manipulator that follows the camera and selected object.

Application

ovwidgets.app.Application starts the app. It initializes the UI runtime, creates the workspace, opens the stage, property, content, and viewport windows, runs the frame loop, and owns the common Python classes that several widgets need.

  • Application owns Settings, SelectionBus, UndoManager, RecentFileList, FrameClock, and call_later().
  • ovwidgets.common supplies ManagedWindow, ErrorReporter, SnapSystem, common style helpers, and mock adapters.
  • Menus, status messages, key routing, theme changes, delayed callbacks, file open requests, and viewport render cadence all meet in this app code.

This is the place to read when a change affects several widgets at once, especially selection, undo, settings, recent files, status messages, or app startup.

Widgets

The widgets in ovwidgets are the visible tools users work with. Each widget owns its child widgets and models, while instances of common Python classes and data adapters carry values between the widgets and the data they show or edit.

  • Stage Browser: StageWindow, StageWidget, HierarchyModel, and StageDelegate show hierarchy rows, type badges, visibility controls, filtering, rename, and drag feedback.
  • Property Inspector: PropertyWindow, PropertyWidget, AttributesWidget, and AttributeModel show selected-object attributes and editors.
  • Content Browser: ContentBrowserWindow, FileBrowserWidget, BackendAdapter, and LocalFSBackend handle file navigation, bookmarks, recent files, import, export, and open-file handoff.
  • Viewport: ViewportWidget, CameraController, TransformManipulator, and ImageBridge handle rendered frames, camera motion, picks, selection outlines, and transform tools.

Read the widget package closest to the visible tool, then follow its adapter calls when the widget needs scene data, file data, properties, transforms, or renderer output.

Data adapters

Common data adapters live in ovui_data_adapters.common and are plain Python. They give widgets a consistent way to ask for stage items, properties, transforms, selection, rendered frames, and undoable commands.

  • Main adapter classes include StageAdapter, PropertyAdapter, TransformAdapter, RendererAdapter, and SelectionAdapter.
  • Shared data names include ChangeEvent, ChangeEventType, AttributeMetadata, BoundCameraPose, GpuFrame, Command, and ZeroCopyState.
  • Mock adapters provide in-memory stage trees, property values, transforms, and frames so widget tests can run without OpenUSD or a GPU.

For another data source, implement these adapter classes and let the same widgets read from that data.

OpenUSD data adapters

The concrete OpenUSD code lives in ovui_data_adapters.openusd. It connects USD stages, USD attributes, transforms, camera data, and renderer frames to the common data adapters.

  • Main classes include UsdStageAdapter, UsdPropertyAdapter, UsdTransformAdapter, and the renderer adapter.
  • Command classes such as SetVisibilityCommand, DeletePrimCommand, and NamespaceEditCommand make USD edits work with UndoManager.
  • Camera, picking, renderer, and session helpers support the viewport when the app is working with USD data.

Read this area when a change needs real USD reads or writes, renderer-backed frames, camera values, picking, or undoable USD edits.

Tests, examples, and entry points

Tests and examples cover the code at several sizes: base UI samples build widgets and scene views, ovwidgets tests drive widgets with mock data adapters, and OpenUSD tests use real USD stages when pxr is available.

  • ovui/examples creates demo windows, markdown widgets, scene manipulators, and image demos.
  • ovui/tests and ovui/standalone/tests cover widgets, scene gestures, frame output, and offscreen runs.
  • ovwidgets/tests covers app startup, widget behavior, mock data adapters, selection, transforms, renderer frames, and OpenUSD adapters.
  • Desktop app start: python -m ovwidgets.app or ovwidgets, optionally followed by a USD file path.
  • Headless app start: python -m ovwidgets.app.headless or ovwidgets-headless, with width, height, or a USD file path.

When looking for a change, start from the entry point or test that matches the user-visible behavior, follow it into the widget, then follow the adapter that supplies its values.
