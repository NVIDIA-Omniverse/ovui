Build choices

What You Can Build With ovui

ovui starts from the same Python idea as Section 1: the kind of tool is chosen before every class name. It can be a small desktop app, a scene workflow, a headless run, or a stream that lets people watch UI output somewhere else.

Standalone Python UI apps
Python opens windows, shows controls, stores values, and reacts to user actions.
Scene tools built from ovwidgets
A tool opens scene data, shows it, edits properties, and keeps larger workflows organized.
Headless rendering and automation runs
Jobs render, capture, and exercise UI flows without a visible desktop.
Live streaming
Rendered output or the app view can be watched from another session when streaming is enabled.

The same Python work can grow from one window into a larger tool, then run or stream where a local desktop is not the only audience.

Standalone Python UI apps

A standalone Python UI app is the smallest useful ovui build. Python opens one or more windows, places controls on screen, keeps values current, and runs user actions when someone clicks, types, drags, or changes a value.

  • Build small tools that collect input, show state, and trigger Python work.
  • Keep app logic in Python while the UI responds to normal user actions.
  • Grow from one window to several widgets when the task needs more room.

This continues the Section 1 starting point without forcing a large app. The first useful result can be a focused Python tool with clear controls and immediate feedback.

Scene tools built from ovwidgets

ovwidgets is the larger build for tools that work with scene data. To start, use widgets that already know how to open scene data, show it, browse it, edit properties, and keep related views moving together.

  • Build tools for opening scenes, inspecting objects, changing properties, and seeing the result.
  • Use data adapters when scene data should come from OpenUSD, mock data, or another Python source.
  • Keep a larger workflow readable by grouping browsing, property editing, content access, and viewport work into widgets.

This is still the same idea as the small Python app, just scaled around a scene task. The workflow is chosen first, then made concrete with widgets and data adapters.

Headless rendering and automation runs

Some tools need the same rendering and UI behavior without showing a desktop window. A headless run lets the app draw, render, capture output, or exercise UI flows on a machine where nobody is using the local screen.

  • Run rendering jobs that need images or screenshots from the tool.
  • Exercise UI flows repeatedly so automation can check what the app drew.
  • Keep scene tools useful in server jobs, batch runs, and remote machines.

The important point is that the build changes, not the product idea. The app can still render widgets, open scene tools, and produce visible output for checks or jobs.

Live streaming

Live streaming extends the same build when the output needs to be seen from another session, browser, or viewer. When configured, a tool can stream rendered output or the full app view while the Python app continues to run in its normal job.

  • Let a remote feedback session watch the viewport or app view without sitting at the GPU machine.
  • Show demos from a browser while the tool keeps running in Python.
  • Make automation output observable elsewhere when a headless job needs a visible result.

ovwidgets and the OpenUSD data adapters support both rendered viewport frames and full-app headless output. The viewport can show whether streaming is off, listening, active, or in error, making the configured app's state visible without assuming every deployment is automatically stream-ready.
