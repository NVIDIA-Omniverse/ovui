Section 8

Data Adapters

Data adapters are the Python objects that let app widgets work with scene data, object values, transforms, renderer frames, and files without baking one backend into the widget code.

Purpose

The widgets receive adapters from the application. The adapter packages explain how data reaches widgets: one package names the plain Python classes and shared records, while the OpenUSD package fills those classes from a real USD stage and renderer.

  • ovui_data_adapters.common holds the shared adapter classes and records used by stage, property, transform, renderer, selection, command, and event code.
  • ovui_data_adapters.openusd contains USD-backed classes for scene hierarchy, object properties, transforms, renderer frames, picking, and undoable USD edits.
  • ovwidgets tests use mock adapters, so stage rows, property rows, viewport behavior, and file browsing can be checked without a USD runtime or GPU.
  • The content browser uses the same adapter approach with BackendAdapter, LocalFSBackend, and file records in ovwidgets.content.backends.

Widgets stay written against common adapter behavior. The app chooses whether the active objects come from mocks, OpenUSD, a renderer, local files, or another backend.

This is why the widgets can be reused. A tree row, attribute editor, or viewport gesture does not need to know how USD stores the value it shows; it needs an adapter object that can answer the widget's question and perform the requested edit.

Common adapter classes

The common package is the plain Python starting point. It avoids external runtime dependencies, exports the adapter class family from ovui_data_adapters.common, and gives mocks and real backends the same class names.

  • StageAdapter supplies root items, children, paths, display names, type names, icons, badge flags, visibility, rename, reparent, filtering, world bounds, and camera pose reads.
  • PropertyAdapter supplies selected paths, attribute names, AttributeMetadata, current values, ambiguity checks, edit begin/set/end calls, change notices, reset support, and the backend scheme name.
  • TransformAdapter reads local and world 4x4 transforms, writes local transforms, and reports whether a selected path can be transformed.
  • RendererAdapter loads a stage, renders RGBA frames, updates resolution, handles point and rectangle picking, updates selection highlight, and shuts down renderer resources.
  • SelectionAdapter, Command, SubscriptionProtocol, and UndoManagerProtocol cover selection conversion, undoable edits, and change subscription handles.

Those classes are intentionally small enough to mock. MockStageAdapter, MockPropertyAdapter, MockTransformAdapter, and MockRendererAdapter prove that the widgets can run from in-memory data while still exercising the same reads, writes, subscriptions, and frame calls used by the full app.

OpenUSD-backed adapters

The OpenUSD package is one concrete backend. Its files import USD, numeric array support, and the renderer only where they are needed, while callers continue to receive the common adapter objects described above. Its renderer path also authors the session RenderProduct data used by ovrtx, including uniform uint[] deviceIds = [0] for ovrtx 0.3 render and pick work.

  • UsdStageAdapter wraps a Usd.Stage, reads hierarchy data, computes visibility and flags, performs rename and reparent edits, emits ChangeEvent, and asks the undo manager to run USD edit commands.
  • UsdPropertyAdapter builds the selected-object property set, converts USD values into Python values, reports range and state metadata, handles multi-selection ambiguity, and writes edited values back to USD.
  • UsdTransformAdapter reads local and world transforms through UsdGeom.Xformable and writes a matrix transform when the viewport manipulator commits a drag.
  • OvRtxRendererAdapter loads stage data into the renderer, updates camera values each frame, returns an RGBA array or GpuFrame, supports point and rectangle picking through renderer queries, and mirrors selection through native ovrtx selection-outline groups.
  • SetVisibilityCommand, DeletePrimCommand, and NamespaceEditCommand make common undo behavior work for USD mutations.

The result is a normal handoff: the app opens a USD stage, creates the USD-backed adapters, gives them to widgets, and the visible widgets continue to use the common adapter methods they already know.

Shared data types

Adapters and widgets pass plain records, enums, and command objects instead of passing raw USD objects through the UI. That keeps the widget code easier to read and makes tests able to create the same kind of data directly in Python.

  • ChangeEvent and ChangeEventType tell the stage browser and application what changed and which paths should be refreshed.
  • AttributeMetadata tells property rows how to label an attribute, choose an editor, show allowed values, show range hints, and mark authored, locked, animated, or large-array values.
  • VisibilityState, ItemFlags, BadgeFlags, and ReparentPosition carry stage-row state without exposing backend objects to the tree widget.
  • BoundCameraPose gives the viewport a saved camera pose when the stage provides one; otherwise the viewport can fall back to framing selected bounds.
  • GpuFrame and ZeroCopyState let renderer output reach ImageBridge while still falling back to a regular RGBA array when direct GPU presentation is unavailable.
  • BackendListEntry, BackendChangeEvent, BackendFileFlags, and BackendResult do the same job for content-browser storage.

These types are the vocabulary that crosses the gap between data and UI. The names describe what the widget needs to know, not how the backend stores it.

How widgets stay backend-independent

Widgets stay backend-independent because they ask adapters for data and send edits back through adapters. The widget owns the visible rows, fields, gestures, filters, and local state; the adapter owns the data source details.

  • The stage browser asks StageAdapter for children, names, type data, visibility, rename, reparent, and change notices.
  • The property inspector receives a PropertyAdapter for the current selection and builds rows from its attribute names, metadata, values, and edit calls.
  • The viewport receives RendererAdapter, TransformAdapter, and StageAdapter objects, so frame output, picking, transform edits, native selection-outline state, and camera framing do not depend on one backend.
  • The content browser receives BackendAdapter, so the same browser model can list, rename, copy, move, delete, and refresh storage entries from local files or another storage backend.
  • New adapters can be added for another scene source, storage source, renderer, or test fixture while leaving the widget code mostly unchanged.

That completes the adapter explanation: ovui supplies core widgets, ovwidgets supplies app widgets, and adapters give those widgets a replaceable data source without forcing every widget to learn every backend.
