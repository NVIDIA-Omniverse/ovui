Section 6

Application

Sections 4 and 5 covered ovui widgets and scene drawing pieces. The ovwidgets application is where those parts become a complete tool, with widgets, menus, status text, settings, selection, undo, themes, startup, and frame timing kept together.

Purpose

The application contains widgets and holds the app state they share. Application starts ovui, creates the docked work area, opens the stage browser, property inspector, content browser, viewport, and related widgets, then keeps selection, settings, undo, recent files, snapping, and deferred callbacks available while the frame loop runs.

  • Startup enters through python -m ovwidgets.app, the ovwidgets console command, or the headless entry point.
  • Application.run() initializes ovui, applies global styles, writes the saved widget placement, applies the chosen theme, and starts run_async().
  • For a headless USD launch, Application.run() preconstructs OvRtxRendererAdapter before ui.init; open_file() reuses that renderer before Usd.Stage.Open so ovrtx owns its loader setup before USD opens the stage.
  • run_async() creates the menu row, status row, widget windows, default mock adapters, shortcut routing, file-drop handling, and the frame loop.
  • When a stage opens, _load_stage() clears old selection, creates data adapters, hands them to widgets, swaps the viewport renderer, and resets render timing.

The application connects visible widgets to data adapters and app state. Widgets render their own views while the app routes selection, settings, undo, status messages, and frame work.

Changes that affect several widgets at once usually start here: startup, shortcuts, file opening, status messages, settings, theme changes, selection, undo, or viewport cadence.

App state classes

Application creates the app-owned Python objects before widget windows are opened. These objects are the handoff points for state that outlives one widget: selection, undo history, settings, recent files, delayed callbacks, snap state, status messages, modal helpers, and frame cadence.

  • SelectionBus owns the selected path snapshot. publish() replaces the snapshot, subscribe() notifies the stage browser, property inspector, viewport, and Layers code, and the event source lets subscribers ignore changes they originated.
  • UndoManager executes Command.do(), keeps undo and redo stacks, exposes undo() and redo(), and can group several commands into one history entry.
  • Settings stores persisted keys such as ui.theme, ui.recent_files, viewport camera defaults, and Layers options. set() notifies subscribers, so menu actions and the settings dialog change live app behavior through the same store.
  • RecentFileList keeps a capped most-recently-used list. Successful open and save paths call add(), then Application writes get_ordered() back to settings for the menu and content browser.
  • call_later() and CallbackHandle route delayed work through the frame loop. The application runs due callbacks before viewport update and render work; widgets use that path for debounced filters, deferred rebuilds, and status clearing.
  • SnapSystem chains snap providers, ManagedWindow wraps widget-window lifetime and themed frame rebuilds, FrameClock gates viewport rendering, StatusBar and ErrorReporter write visible status text, and dialog helpers such as confirm_dialog() and save_file_dialog() keep modal callback handling in one place.

Widgets receive the object or callback they need, update it through its public method, and let subscribers or the next frame carry the visible result. That keeps selection, settings, commands, and status text consistent without requiring widget-to-widget imports.

Sources

The application source is split by job. Start with application.py when the behavior involves startup or several widgets, then move to the smaller file that owns the visible feature or common class.

  • ovwidgets/ovwidgets/app contains application.py, the main source for startup, widget creation, file opening, adapter handoff, frame updates, and shutdown.
  • The same app package contains menu_bar.py, status_bar.py, and settings_dialog.py, which own the visible app chrome around widgets.
  • ovwidgets/ovwidgets/common owns common Python classes, widget-window helpers, mock adapters, style resources, and test-friendly stand-ins.

How app state reaches widgets

App state reaches widgets through ordinary Python objects. Application creates instances of common Python classes first, then passes explicit objects such as selection, undo, settings, recent files, or an open-file callback when a widget needs them.

  • Selection travels through SelectionBus.publish() and subscribe(); widgets compare the event source when they need to avoid echoing their own change.
  • Settings travel through Settings.get(), set(), and subscribe(); theme changes call set_theme() and rebuild widget backgrounds.
  • Commands travel through UndoManager.push(), undo(), and redo(); menus and shortcuts read the same undo state.
  • Data reaches widgets when Application._load_stage() calls widget setters such as set_adapter(), set_property_adapter_factory(), attach_stage(), and set_renderer().
  • Delayed work reaches widgets when call_later() adds a callback and _on_frame_update() runs due callbacks before viewport update and render work.

The result is readable: instances of common Python classes keep selection, settings, commands, and current data; widgets read from or update those objects; adapters feed widget models; and ovui redraws the visible result on the next frames.
