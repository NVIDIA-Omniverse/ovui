ovui Project Overview

ovui is a Python UI framework, a library of ready-made app widgets, and a runnable reference application for building scene, viewport, and data tools that look polished and behave consistently. The Python-facing UI layer (ovui) supplies the primitives; ovwidgets supplies the app widgets (stage browser, property inspector, content browser, viewport, composition view); data adapters connect those widgets to OpenUSD or custom backends; the supplied application wires everything together; and an inspector pipeline lets people and AI coding agents drive the running UI through the same screenshot-action loop.

What ovui is

ovui gives Python code a UI layer for windows, rows, columns, labels, buttons, menus, inspectors, browser views, viewports, and related app UI. It includes lower-level primitives for focused controls and higher-level app widgets for complete views, so the same toolkit can support a single control area or a larger application view.

  • Python-facing UI layer: windows, layout containers, controls, styling, value models, menus, images, markdown, screenshots, and frame-driven updates.
  • App widgets, examples, and supplied app code: stage browsing, property inspection, content browser workflows, composition views, viewport interaction, menus, status feedback, settings, recent files, selection, undo, and shortcuts.
  • Scene and viewport pieces: scene drawing, camera gestures, picking, selection outlines, transform manipulators, rendered frames, and viewport status feedback.
  • Data and state adapters: adapters connect widgets to OpenUSD stages, local files, ovrtx rendering, in-memory test data, and project-specific data sources without forcing each widget to know every backend detail.
  • Fast iteration: views are ordinary Python code, so a tool can be run and inspected while the view code is still changing.

The result is a toolkit with both UI vocabulary and application structure. Python describes the visible view; models and adapters carry values, hierarchy, files, transforms, rendered frames, and selection between the view and the data behind it.

The project in three parts

The repository is easiest to understand by following the path from UI primitives to app workflows and then to data. The base layer supplies the Python UI vocabulary. ovwidgets adds application views and app state. Scene, viewport, and adapter code decide where hierarchy data, attributes, files, transforms, and rendered frames come from.

ovui supports several adoption depths: keep the full application, use selected widgets, write a new adapter behind an existing widget, or build directly from the Python UI layer.

  • Python UI layer: use this when a tool needs custom controls, layouts, styling, markdown, image display, screenshots, scene drawing, or a focused Python view without the supplied application.
  • App widgets and application views: use these when a tool needs stage browsing, property inspection, content browsing, composition views, viewport work, menus, status feedback, undo, settings, recent files, and shared selection.
  • Scene, viewport, and data adapters: use these when the visible workflow should read or edit OpenUSD, local files, rendered frames, mock data, or another backend.

These parts explain why the repository contains UI primitives, app widgets, a runnable application, scene tools, and adapters in one place. They are different entry points into the same tool-building system, not separate demos competing with each other.

Ways to use ovui

A project can adopt ovui from the supplied application, from one app widget, from an adapter boundary, from the Python UI layer, or as a set of reference patterns for an AI coding agent. Those paths can be mixed when the tool grows.

  • Run the complete application. Use it as a working reference for how menus, status feedback, settings, recent files, shortcuts, file opening, drag and drop, shared selection, undo, widgets, viewport cadence, and backend wiring fit together.
  • Add or extend an app widget. Place a stage browser, property inspector, content browser, viewport, or composition view into a product workflow, then adjust filtering, display, editing behavior, toolbar actions, or viewport tool behavior as needed.
  • Keep widgets and replace the data. Connect a stage browser, property inspector, viewport, content browser, or composition view to proprietary data, a remote backend, local storage, generated data, or a test backend.
  • Write new data adapters. Use adapters as the connection point for hierarchy data, attributes, transforms, rendered frames, content browsing, and composition data.
  • Use the ovui API directly. Build focused controls from windows, stacks, fields, tree views, menus, markdown, image providers, styles, screenshots, scene views, gestures, and manipulators; app widgets can still be mixed in later.
  • Use ovwidgets as skills for Claude Code, Codex, or Cursor. The repository ships Claude Code-compatible skills in skills/: skills/omniverse-ui-apis for atomic ovui construction, skills/omniverse-ui-widgets for composing standalone apps from the existing widget set, and skills/omniverse-ui-inspector for driving a running app through a screenshot-first inspector. Pointing an AI coding agent at these skills hands it the proven layout, model-view, styling, adapter, and inspector patterns the supplied application already uses, so the generated tool starts from real ovwidgets components and patterns rather than generic UI code, and looks and behaves like the rest of the toolkit.

These choices can be combined: begin with the full application, replace one backend, add one widget, reuse the content browser, build a custom tool area from UI primitives, and let an AI coding agent generate the next tool by reusing ovwidgets through the skills above. ovui is organized so a project can take the amount that matches the tool's goal without rewriting every piece at once.
