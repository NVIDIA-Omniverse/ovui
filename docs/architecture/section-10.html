Section 10

Startup, Data Flow, and Verification

After the widgets and adapters are in place, an ovui-widgets run starts the app, creates instances of common Python classes, opens or creates a stage, gives adapters to widgets, advances frames, and checks those behaviors with tests and examples.

The two starts converge on the same Application code. From there, file opening, shared state, widget updates, viewport frames, and checks run through named modules and tests.

Desktop startup

The desktop entry point is python -m ovui_widgets.app, with the ovui-widgets console command doing the same startup work. The entry code parses one optional USD file path, creates Application, and calls Application.run().

  • run() initializes ovui, applies global styles, applies the saved theme, records the startup file path, and hands run_async() to ui.run().
  • run_async() creates the docked work area, menu row, status row, stage browser, property inspector, content browser, composition stack, and viewport.
  • The first frame gives the windows time to exist before saved placement is restored.
  • If a startup file was passed, open_file() runs after the UI exists; otherwise the app creates a new empty stage and loads it through the same handoff.

The important point is that startup does not special-case the real widgets. It builds the same visible app first, then swaps mock startup data for real stage-backed data when a file or default stage is ready.

Headless startup

The headless entry point is python -m ovui_widgets.app.headless, with ovui-widgets-headless as the console command. It chooses the offscreen frame size before importing the application, then creates Application and calls run() with the optional USD path.

  • --width and --height choose the frame size for automation, render capture, or streaming jobs.
  • The same run_async() body creates widgets, instances of common Python classes, startup data, shortcuts, file drops, and the frame loop.
  • Optional streaming and remote input setup happens only after the first drawn frame, so a plain headless run can stay focused on rendering or automation.

Headless startup changes where the app draws, not how the app is assembled. Stage opening, adapter handoff, viewport update, and tests keep using the same app code.

Runtime frames

Once the app is running, run_async() advances one frame at a time. Each pass drains queued remote input and queued app messages, waits for ui.next_frame(), then lets the application update callbacks and viewport work.

  • call_later() stores callbacks as CallbackHandle objects; _on_frame_update() fires due callbacks and removes completed ones.
  • The viewport update runs every tick, so camera flight and inertia keep moving even when rendering is throttled.
  • FrameClock decides when rendering is due; it commits only after ViewportWidget.render() returns True.
  • A successful render asks the active RendererAdapter for a frame, sends it through ImageBridge, updates HUD values, and keeps scene drawing aligned with the camera.
  • Exit requests flip the running flag, and the run_async() cleanup code releases windows, subscriptions, adapters, callbacks, and shared singletons.

This keeps frame work predictable. User input and queued messages land before the next draw, rendered pixels land after the render gate allows them, and cleanup runs from the same application owner that created the objects.

Stage loading

A stage can enter through open_file() or open_stage(). File startup uses open_file(): it prepares the renderer adapter, opens the USD file, then calls _load_stage(). In-memory and automation runs can pass an existing stage to open_stage(), which also lands in _load_stage().

  • _load_stage() cancels the old stage subscription, clears selection, and detaches prior composition state before the new stage becomes active.
  • UsdStageAdapter becomes the app's active stage adapter and is handed to the stage browser.
  • The property inspector receives a factory that creates UsdPropertyAdapter objects for the current selection.
  • The viewport receives UsdTransformAdapter, the active stage adapter, undo, snapping, the scene name, and a renderer adapter loaded with the stage.
  • The composition stack receives its composition data object, and the viewport clock resets so the next eligible tick paints the newly loaded stage.

The same handoff also updates recent files, stage-change subscriptions, renderer selection highlight, prim counts, and initial camera placement. Opening a file therefore changes the active data objects while the visible widgets keep their jobs.

Data flow

Data moves in both directions. A read flow brings scene hierarchy, attributes, transforms, files, and rendered pixels into widgets. A write flow sends user edits back through adapters and instances of common Python classes so undo, selection, notices, and redraws stay together.

  • A stage-browser selection publishes through SelectionBus; the property inspector rebuilds for the selected paths, and the viewport reapplies selection highlight.
  • A property edit goes through adapter edit calls and UndoManager; stage-change notices then refresh affected widgets and notify the viewport renderer.
  • A viewport transform drag uses PrimTransformModel, TransformAdapter, snapping, and undo to write object transforms as one user action.
  • A rendered frame comes from RendererAdapter.render_frame(), enters ImageBridge.update(), and reaches the viewport image provider.
  • A content-browser open action calls the explicit open_file callback, so file browsing can stay separate from scene selection.

The application is the meeting point for that data movement. Widgets own their visible rows and gestures, adapters own data access, and instances of common Python classes carry the state that must be seen by more than one widget.

Tests and examples

The repo checks the behavior at several sizes. ovui tests and examples prove base widgets, scene drawing, images, and standalone frames. ovui-widgets tests then cover application startup, stage opening, adapter swaps, widget behavior, frame cadence, headless startup, streaming hooks, and user-like screenshot flows.

  • ovui-widgets/tests/test_application.py checks singleton state, common Python classes, call_later(), frame callbacks, settings, and shutdown.
  • ovui-widgets/tests/test_step26_open_file.py checks open_stage(), open_file(), stage adapter creation, invalid-file handling, and subscription cleanup.
  • ovui-widgets/tests/test_application_frame_cadence.py and ovui-widgets/tests/test_viewport_throttle.py check the update/render split and FrameClock behavior.
  • ovui-widgets/tests/test_headless_entrypoint.py, test_application_headless_export.py, test_input_drain.py, and test_application_message_drain.py check headless entry, per-frame export, input ordering, and queued app messages.
  • ovui/examples, ovui/tests, and ovui/standalone/tests cover the base UI, scene package, image paths, screenshots, and standalone frame behavior.

Those checks prove the run: the same code can start with a desktop window or a headless frame, load data, update widgets, render output, and verify the behavior with focused tests and visible examples.
