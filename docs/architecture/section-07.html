Section 7

Widgets and Data Adapters

After the ovui widgets, scene drawing tools, and application are in place, ovwidgets has enough structure for app widgets that can be kept, derived from, copied, or replaced when building a scene tool.

Purpose

The app widgets are ordinary Python widgets, but each one reads through an adapter instead of hard-coding a single backend. That keeps the visible workflow stable while the app decides whether the data comes from startup mocks, an opened USD stage, local files, or a renderer.

  • Widgets own their docked window, inner widget, model objects, delegates, filters, and local gestures.
  • Adapters supply hierarchy, attributes, files, rendered frames, transforms, and composition state.
  • The application creates or swaps adapters when a stage opens, then calls widget methods such as set_adapter(), set_property_adapter_factory(), attach_stage(), and set_renderer().
  • App state classes such as SelectionBus and UndoManager, plus settings, status text, and deferred callbacks, keep selection, command history, and visible messages consistent.

The application is the meeting point. Widgets stay focused on their own UI, while adapters provide the data each widget needs to draw and edit.

This organization is the practical reuse point for ovwidgets. The viewport can stay in place while the renderer is replaced, the content browser can stay in place while storage is replaced, or the property inspector can stay in place while new property sections are added, all without rewriting the rest of the app.

Stage browser and scene data

The stage browser turns scene hierarchy into a tree the user can search, expand, select, rename, and reorganize. StageWindow owns the docked window; StageWidget owns the search bar, tree, footer counts, selection wiring, rename controller, and drag target feedback.

  • HierarchyModel wraps StageAdapter for ui.TreeView and lazy-loads children as rows are expanded.
  • StageDelegate draws type labels, visibility state, badges, branch icons, and row styling.
  • StageAdapter supplies roots, children, display names, type names, item flags, badge flags, visibility, rename, reparent, filter support, and change notices.
  • Selection travels through SelectionBus, so a tree click can update the property inspector and viewport without direct imports between widgets.

The browser is therefore useful beyond the default app. A new scene backend can provide the same adapter behavior and still reuse the tree, filtering, visibility column, rename flow, and selection sync.

Property inspector and object data

The property inspector follows selection. When selected paths change, PropertyWindow asks its factory for a fresh PropertyAdapter, then rebuilds the visible sections for those objects. The widget does not need to know how the backend stores attributes.

  • AttributesWidget is the default catch-all property section; it groups attributes from metadata and builds rows for supported value types.
  • AttributeModelBase handles value reads, buffered edits, write-through edits, ambiguity checks, and change subscriptions for individual rows.
  • PropertySchemeRegistry lets additional property sections opt into a selected payload while the default attribute section remains available.
  • The adapter supplies selected paths, attribute names, metadata, current values, per-component ambiguity, reset support, and edit begin/set/end calls.

That matters when richer inspectors are added. A specialized property section can sit beside the default attribute list, use the same selection payload, and leave the backend handoff in the application.

Content browser and files

The content browser is about files, not scene selection. ContentBrowserWindow creates a FileBrowserWidget with a backend, a start URL, bookmark and recent-file state, settings, and an explicit open-file callback.

  • BackendAdapter supplies URL cleanup, stat, directory listing, folder creation, copy, move, delete, parent lookup, basename lookup, and optional change watches.
  • LocalFSBackend is the default local-file implementation, while the widget code remains written against the backend adapter.
  • FileBrowserWidget owns navigation, search, file detail rows, grid view, renaming, drag and drop, delete confirmation, bookmarks, and recent files.
  • File selection intentionally does not publish to SelectionBus, because file URLs are not scene paths.

The separation is small but important. The browser chrome can stay in place while storage is replaced, and local storage can stay in place while the open-file handler changes.

Viewport and rendered output

The viewport combines rendered pixels with scene interaction. ViewportWidget owns the toolbar, rendered image, SceneView gestures, HUD values, selection outline, camera controller, and transform manipulator.

  • RendererAdapter loads the stage into the renderer, renders RGBA frames, supports picking, rectangle picking, selection highlights, and shutdown.
  • ImageBridge pushes the returned frame into an ovui image provider so the viewport can show renderer output.
  • CameraController handles orbit, pan, zoom, look, focus, view matrices, and projection matrices.
  • PrimTransformModel uses TransformAdapter, StageAdapter, UndoManager, and snapping to drive drag edits on selected prims.

The viewport is reusable because rendering, transforms, selection, and camera motion meet through explicit objects. A renderer swap changes where frames come from; the toolbar, camera gestures, HUD, and manipulator can remain the same.

Composition stack data

The composition stack answers a different question from the stage browser: not which prims are visible in the hierarchy, but where scene opinions come from and which entry receives new authoring. It shows an ordered composition stack, dirty state, save actions, mute and lock controls, missing-file signals, authoring target state, and optional prim-spec rows.

  • The app creates the object that supplies composition data when a USD stage opens, attaches its notices through call_later(), and hands it to the widget with set_adapter().
  • The widget keeps its own tree model, cell delegate, options menu, context menu, footer actions, selection watcher, and save-all model.
  • The adapter supplies root and session entries, ordered child identifiers, display names, save state, mute state, lock state, authoring target, file permissions, and prim-spec descriptors.
  • Commands wrap save, reload, authoring target, mute, lock, insert, create, remove, move, merge, and flatten actions so undo and redo stay with the rest of the app.

This widget can stay in place when composition inspection is needed, or be removed when a simpler tool only needs a stage browser and viewport. Its composition data stays separate from the other widgets, so either choice leaves those widgets intact.

How widgets stay independent

ovwidgets keeps the widgets independent by making the application responsible for shared state. A widget can be tested with mocks, used inside the full app, or swapped for a custom widget because it receives the objects it needs instead of reaching across to sibling widgets.

Injected adapters
Widgets receive the data reader or writer they need. Tests pass mocks; the running app passes USD-backed or renderer-backed objects.
App state classes
SelectionBus, UndoManager, settings, status text, and call_later() route selection, command history, visible messages, and delayed work.
Focused ownership
Each widget owns its own UI model, delegate, local filters, gestures, and cleanup without importing sibling widgets.

The result is predictable composition: replace one widget or one data source, then keep the same selection, undo, settings, and frame timing rules.

  • Stage browser, property inspector, viewport, composition stack, and content browser are created by the application, not by each other.
  • Stage browser, property inspector, viewport, and composition stack react to scene state; content browser stays file-oriented and opens files through a callback.
  • Adapters isolate backend work from UI behavior, so tests can cover widget behavior without requiring a GPU or a real USD file.
  • When a new app widget is needed, the common pattern is to own the visible rows locally, receive data through an adapter, and use instances of common Python classes for app-wide state.

The same idea carries into the adapter packages themselves. Shared data records and concrete USD-backed implementations keep backend behavior separate from the widgets that read and edit it.
