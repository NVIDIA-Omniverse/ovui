Section 4

UI Framework

ovui gives Python code the base UI runtime used by standalone apps and widgets in ovwidgets: windows, layout containers, widgets, value models, callbacks, and an async frame loop.

Purpose

Python code imports the package with import omni.ui as ui. The package loads bound C++ UI classes and, outside a larger app, adds standalone helpers such as ui.init(), ui.run(), ui.run_async(), and ui.next_frame().

  • ui.Window creates a window; window.frame is where child widgets are added.
  • ui.VStack, ui.HStack, ui.ZStack, and related containers arrange child widgets.
  • Fields, sliders, progress bars, and trees read from model objects; buttons and tree widgets call Python callbacks.
  • ui.run() drives the frame loop, and await ui.next_frame() waits for a rendered frame.

The frame loop keeps the UI active: Python creates the parts, models carry values, callbacks run Python work, and the window redraws.

The result is a small Python app: create a window, add widgets, wire model values or callbacks, then let the frame loop keep drawing and handling input.

Python classes

Most app code meets a compact set of classes first. These names appear in the Python package docs, examples, tests, or bindings, and they are enough to read common app code without a full class inventory.

  • Window, Frame, Workspace, and DockSpace create windows and docked work areas.
  • VStack, HStack, ZStack, ScrollingFrame, and Spacer arrange widgets.
  • TreeView, AbstractItemModel, and AbstractItemDelegate handle tree-style data.
  • AbstractValueModel, SimpleStringModel, SimpleFloatModel, SimpleIntModel, and SimpleBoolModel carry values for fields, sliders, checkboxes, and progress bars.

Common widgets

The common widgets cover text, commands, editable values, hierarchical views, images, markdown, progress, and menu actions. Widgets in ovwidgets reuse these widgets instead of drawing a separate widget set.

  • Text and display: Label, Image, ImageWithProvider, MarkdownWidget, and ProgressBar.
  • Controls: Button, ToolButton, CheckBox, ComboBox, RadioButton, and RadioCollection.
  • Editable values: StringField, FloatField, IntField, FloatSlider, IntSlider, FloatDrag, and IntDrag.
  • Structured views: TreeView reads an item model and can use a delegate to build row widgets.

The examples show the everyday pattern: create widgets inside a frame, set model values with set_value(), and attach callbacks such as clicked_fn where user action should call Python code.

Debugging usually starts from Python use, checks the binding, then inspects the C++ widget code when native behavior owns the result.

  • The Python package imports _ui, style helpers, markdown helpers, and standalone runtime functions.
  • The C++ core defines widget behavior, layout calculation, styling, image providers, and rendering support.
  • The Python bindings expose classes such as Window, Frame, Button, TreeView, and model classes.
  • Examples and tests show real use: showcase widgets, markdown, images, scene tools, model updates, input helpers, and screenshot checks.

How data reaches widgets

Data enters widgets through models and callback functions. The base UI framework does not know about USD; widgets in ovwidgets can ask a data adapter for values, put those values into item or value models, and let ovui widgets render them.

  • AbstractValueModel stores one value and exposes bool, float, int, and string accessors, plus value-changed and edit callbacks.
  • AbstractItemModel exposes child items and value models per item; TreeView asks it for rows and values.
  • AbstractItemDelegate can build row widgets, so the same tree model can draw names, icons, badges, fields, or checkboxes.
  • Buttons and menu items call Python functions through callbacks such as clicked_fn or setter callbacks.
  • Adapter-fed widgets use a direct handoff: a data adapter feeds a widget model, and the widget model feeds ovui widgets.

For a new widget behavior, start with a small Python app, confirm the model and callback flow, then inspect the C++ core or Python bindings when the behavior needs native widget changes.
