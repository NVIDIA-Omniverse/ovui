Section 11

Inspector Pipeline

ovui ships a first-class inspector pipeline for an AI agent to drive the running application the same way a person would: by looking at the screen, moving the mouse, clicking, and typing on the keyboard. The pipeline is part of ovui itself, not an external tool wired on top.

How the agent works

The pipeline follows a single loop. The agent captures the current screen, decides what to do based on what it sees, performs one input action, captures the screen again, and verifies that the new picture reflects what it just did. Every interaction follows that cycle: screenshot, analyze, act, screenshot, verify. There is no internal API access and no programmatic shortcut; the agent uses only what is visible and reachable through the same input path a person would use.

  • The agent reads the screen from a screenshot only, never from internal state inspection or debug consoles.
  • Targets are chosen from pixels in the most recent screenshot, not from saved guesses.
  • One action runs between screenshots, so the next picture proves whether the action worked.
  • Failures are reported with the screenshot that shows them, not patched silently in code.

That style is what makes the pipeline a usable QA path. Tests that take shortcuts often pass when the visible product is broken; tests that follow the see-act-see loop fail when the user would also fail, and pass when the user would succeed.

What the agent can do

The pipeline groups its work into capture, mouse input, keyboard input, and frame timing. Each capability is provided by ovui through the same running application that draws the UI, so the agent does not need a separate route for a tree row, a menu item, a filter field, a viewport gizmo, or a dialog.

  • Screenshot capture. A programmatic call returns the current contents of the application window. This is how the agent sees. Every action is preceded and followed by a screenshot so the result of the action is recorded as an image.
  • Mouse control. Calls move the cursor to a target, click left, right, or middle, double-click, drag with mouse-down and mouse-up steps, and scroll. The target is always a pixel taken from a recent screenshot.
  • Keyboard control. Calls type plain text, press keys, and perform modifier-key flows when a workflow requires them.
  • Frame timing. Calls let the agent wait for layout, rendering, hover, focus, callbacks, and animation to settle before it compares the next screenshot.

Those categories are enough to drive any visible widget. The agent reaches each target by where it appears on screen, then waits for the next frame before deciding whether the visible state changed as expected.

Available control APIs

The public control API lives in omni.ui.testing. It is intentionally small: one helper captures the window, a group of helpers injects mouse input, another group injects keyboard and text input, and the frame helpers keep the agent aligned with the application loop.

  • Capture. capture_screenshot records the rendered application window. The helper uses ovui's scheduled pre-swap capture path when it is available, with a direct capture fallback.
  • Mouse. mouse_move, mouse_click, mouse_double_click, mouse_drag, and mouse_scroll cover hover, press, release, drag, and wheel-style input.
  • Keyboard and text. type_text writes text into the focused widget, and press_key presses and releases an ImGui key. Modifier-key flows can drop to the lower _ui._inject_key_event hook when the public helper is not enough.
  • Frame timing and run loop. wait_frames and next_frame advance the UI before the next screenshot. ui.run and ui.run_async are the run-loop entries that keep the app and the agent's coroutine moving together.

Below those helpers, omni.ui._ui is the pybind layer that reaches the standalone backend. The public helpers are the normal agent-facing API; the lower hooks exist so tests can cover input cases that need exact event timing without mutating widget models or scene data directly.

How the agent connects and runs

The connection is an in-process Python bridge, not a network session or an external debugger. A standalone ovui app starts its normal run loop with ui.run or ui.run_async. The QA client runs beside the app code as an async routine, imports omni.ui.testing, and calls the helpers that are already bound to the live ovui backend.

  • The app starts with the ovui standalone backend initialized. In headless runs, the backend renders offscreen, but the same testing helpers still capture the rendered frame.
  • The agent attaches by importing omni.ui.testing in that same Python run. The helpers call through omni.ui._ui, which is the pybind layer connected to the active backend.
  • Screenshot capture schedules a readback from the frame that ovui just rendered. Mouse and keyboard helpers enqueue input into the backend, which then feeds ImGui and the ovui widgets during the next frame.
  • The run loop is therefore concrete: start the app with ovui testing available, wait for the first stable frame, capture, choose the visible target, perform one input action, wait, capture again, and validate the new image.
  • When a particular input style needs the operating system level path rather than the application-level path, that distinction is reported as part of the run, not worked around silently.

This keeps the inspector pipeline honest. The agent runs close enough to the app to use ovui's capture and input APIs, but it still judges success from screenshots instead of internal state. That is the same loop a person performs when sitting in front of the application.

Using the pipeline from Claude or Codex

The same pipeline drives the running app from an AI coding agent such as Claude Code, Codex, or Cursor. The repository ships a Claude Code-compatible skill, skills/omniverse-ui-inspector, that wraps the omni.ui.testing helpers in a localhost HTTP server and exposes a small CLI so the agent does not call internal APIs.

  • Launch the app with the skill on PYTHONPATH. Run PYTHONPATH="${OVUI_REPO}/skills/omniverse-ui-inspector:${PYTHONPATH:-}" python -m ovwidgets.app (or python -m ovwidgets.app.headless for offscreen runs). Importing the ovuiinspect module starts a localhost FastAPI server on 127.0.0.1:9910 in a background thread; ovui then drains queued mouse, keyboard, and screenshot actions on the normal frame loop. Defaults can be overridden with OVUIINSPECT_HOST, OVUIINSPECT_PORT, and OVUIINSPECT_ENABLE_EXECUTE.
  • Drive the app through the ovui-inspect CLI. The agent issues skills/omniverse-ui-inspector/scripts/ovui-inspect wait --timeout 60 once the app starts, then screenshot --out file.png, move X Y, click X Y, type "text", press KEY, combo "CTRL+A", drag X1 Y1 X2 Y2, and scroll. Coordinates always come from the previous screenshot, never from guesses.
  • Follow the screenshot-action-screenshot loop. The agent prompt must require: take a screenshot, identify the target pixel from that image, perform one atomic action, take another screenshot, and compare. One action per screenshot pair. No batching, no Python execution shortcuts, no /execute unless the app was explicitly relaunched with OVUIINSPECT_ENABLE_EXECUTE=1 for a setup step that has no visible UI path.
  • Pair the inspector with the code-generation skills. Point the agent at skills/omniverse-ui-apis (atomic ovui primitives and TreeView/Window/Scene patterns) and skills/omniverse-ui-widgets (composing standalone apps from existing widgets) when asking it to generate or modify ovui code. The inspector skill captures what the running UI actually looks like; the code skills supply the proven layout, model, styling, and adapter patterns. Used together, the agent sees the live state, reads the right patterns, edits code, then re-screenshots to verify the change.

A useful agent prompt names all three pieces explicitly: which app to launch, which inspector commands to run between edits, and which skill to consult for code patterns. Example: "Launch python -m ovwidgets.app with skills/omniverse-ui-inspector on PYTHONPATH, wait for health, screenshot the current viewport, add a new toolbar button to ViewportWidget using the patterns in skills/omniverse-ui-widgets/SKILL.md, then re-screenshot and confirm the new button appears."

Grounding the agent in screenshots from the running app and in the skills above is what makes the generated UI look and behave like the rest of ovui instead of generic code: the agent reuses real ovwidgets components, follows the styling and selection conventions the application already enforces, and proves the change with a screenshot the user can read.
