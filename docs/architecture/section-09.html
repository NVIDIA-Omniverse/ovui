Section 9

Renderer Frames and Selection Outline

After the adapters are in place, two flows keep the viewport coherent: rendered pixels travel from the ovrtx renderer to the viewport image each frame, and selection travels between the stage browser, the viewport, and the property inspector through one shared object.

From ovrtx to the viewport image

The viewport is a handoff point, not a second renderer. ovrtx renders the current stage from the current camera view, then ViewportWidget asks the renderer adapter for the next image that matches that view. ImageBridge hands the result to ovui in the form the image widget can display, and the viewport keeps camera input, picking, and selection feedback attached to the image the user sees.

  • ovrtx owns the render work: it receives the stage and camera state and produces the frame image.
  • The OpenUSD adapter authors the viewport session RenderProduct, including uniform uint[] deviceIds = [0], so ovrtx 0.3 uses the expected device for render and pick work.
  • OvRtxRendererAdapter is the app-facing renderer object, so the viewport can request frames without carrying ovrtx setup details.
  • ImageBridge accepts either a GPU-backed GpuFrame or a CPU RGBA image and gives it to ByteImageProvider.
  • ui.ImageWithProvider shows that provider inside the viewport while SceneView keeps camera gestures and picking aligned with the visible image.

That split keeps responsibilities clear. The renderer adapter knows how to speak to ovrtx, the bridge knows how to feed ovui image data, and the viewport knows what the user is looking at and interacting with.

Zero-copy and CPU fallback

The image handoff has a fast route and a fallback route. When zero-copy is enabled and ovui accepts GPU-backed image data, the bridge can display a renderer frame without first copying it through CPU memory. When that is not available, the renderer returns a normal RGBA image that the same provider can display.

  • ZeroCopyState records whether GPU presentation is disabled, being probed, enabled, or in fallback.
  • GpuFrame represents the GPU-backed frame long enough for ImageBridge to give it to ovui.
  • If ovui accepts the GPU-backed frame, later frames stay on that route. If not, the state switches to CPU fallback.
  • The CPU route gives the provider a compact uint8 RGBA image, so the viewport still displays the same frame content.

The viewport does not need a separate drawing path for these cases. It asks for a frame, hands the result to the bridge, and lets the bridge choose the form the image provider receives.

Selection across widgets

Selection is the second shared flow. The stage browser, the viewport, and the property inspector each show selection in a different way, but none of them has to call the others directly. A change goes to SelectionBus, and each widget updates its own display from the same selection state.

  • The stage browser publishes selection when the tree changes, and it listens for selection that starts in the viewport.
  • The viewport listens for selection so its renderer-owned highlight and native ovrtx outline match the current item set.
  • The property inspector listens for the same selection and rebuilds around the selected scene items.
  • SelectionBus is the meeting point, which keeps sibling widgets independent while still making them move together.

The important architectural point is the direction of communication. A widget changes selection once, the bus records it once, and the other widgets react to that one change instead of forming direct links to each other.

Selection outline and picking

Picking starts from the image the user is looking at. A click or drag in the viewport asks the renderer what scene item is under the current pixel or rectangle for the current view and RenderProduct. The result becomes the app selection through SelectionBus, and the viewport sends that selection back to the renderer-owned outline and highlight path.

  • PickGesture handles a point click, while PickRectGesture handles drag selection.
  • OvRtxRendererAdapter enqueues point and rectangle pick queries, tracks in-flight queries in FIFO order, drains canceled callbacks, and preserves the latest hit when ovrtx collapses rapid same-RenderProduct replacement queries.
  • RendererAdapter answers the pick using the same stage, camera view, and RenderProduct that produced the rendered frame.
  • The viewport publishes the renderer's answer to SelectionBus, so the stage browser and property inspector follow the pick.
  • Selection feedback is renderer-owned: set_selection_highlight() configures native ovrtx selection group styling and writes selection-outline group deltas only for paths whose state changed.

The loop stays readable because each part owns one visible result. The bus owns what is selected, the renderer owns the image, pick answers, highlight, and native selection outline, and the viewport owns the user gesture that starts the change. New selection tools can join by publishing a selection change through the same path.
